## A. 总体结论（Executive Summary）

**成熟度**：核心创作链路（选照片 → 自动排版 → 编辑 → 保存 → 阅读）完整，自动化测试覆盖很广（97 个浏览器套件，其中 96 个通过；299 个单元测试）。

数据可靠性已经有不少防线：
- 启动时读不出数据，会停在救援页，绝不会生成一个空白手帐；
- 媒体写入后会回读校验；
- 切到后台时立即保存；
- 媒体永远不会被删除。

**主要优势**
- 完全本地、离线可用，没有第三方 SDK，也不收集任何数据。
- 页面数据和显示尺寸无关：用百分比坐标和固定的 4:5 纸张。
- 删除页面、恢复失败都不会丢失媒体文件。

**最大风险**
1. **备份**：
   - 媒体超过 100 MB 就无法备份；
   - 恢复会整份替换，替换前不留快照；
   - 能做出来的备份，可能恢复不了（mime 校验）；
   - 「成功」靠用户自己确认，App 没有校验。
2. **数据只存在这台设备上**：卸载 App 或者换手机时，没有自动的安全网（iCloud 整机备份是否覆盖 WebKit 数据，需要真机验证）。
3. **发布材料缺失**：
   - 没有隐私清单（`PrivacyInfo.xcprivacy`），而 Swift 用到了 `UserDefaults`；
   - 仓库里没有隐私政策；
   - 普通用户能看到「实验室」和「测试记录」，里面是社区等没有服务器的演示功能。
4. **界面承诺和实际不一致**：
   - 有几处删除提示写着「可以撤销」，实际上不能撤销；
   - 隐私说明暗示照片和视频都去掉了位置信息，实际只有照片去掉了。
5. **适配**：
   - 不跟随系统字体大小，也不跟随系统深色模式；
   - 在 iPhone Duo 外屏上，设置齿轮被状态栏挡住（【实测】）。

## C. P0 数据完整性与恢复

### C1. 数据损坏保护（现状）

- **写入**：先同步写 localStorage 镜像，再异步把整份 JSON `put` 进 IndexedDB（合并写入）；`stored()` 会等到真正写完（`model.mjs:470-518`；`meta-store.mjs:46-63`）【代码】。
- **快照校验**：写入前会用 `validateStateSnapshot` 检查字段类型、页面 id 是否唯一、有没有危险的键名，不合格的状态不会写入（`model.mjs:288-431`）【代码】。
- **启动**：由 `decideJournalOpen` 决定（`journal-open.mjs:72-109`）：
  - 本地副本有效时就用它；
  - 损坏时，如果 IndexedDB 里的副本有效，提供「使用较早的副本」；
  - 版本不兼容（`schemaVersion` 不是 1）时两份都不动；
  - 打不开或丢失时，进入救援页（`app.js:13030-13090`）。**绝不会用一个空白手帐覆盖原有数据。**
- **不足**
  1. 没有历史快照，只有一个 `little-days.v1.rescue` 槽位，而且每次都会被覆盖。
  2. 没有校验和，也不知道是哪个 App 版本写的。
  3. `logEvent("journal-blocked")` 的名字里有连字符，不符合命名规则 `/^[a-z_]{2,32}$/`（`events.mjs:32`），所以**救援事件从来没有被记录下来**【代码】。
- **建议**（最小改动）
  - 在 meta 数据库里保留滚动快照：每天第一次成功写入时，把前一天的 state 复制一份到 `little-days.v1.snap.<日期>`，保留最近 3 份。只新增键，不改结构；每份只有几 MB。
  - 在 state 里加一个可选字段 `writer: {app: "10.64", at}`，用来排查问题。
  - 改正那个事件名。
  - 救援页里增加「从快照恢复」。

### C2. 自动保存的可靠性

- 450 ms 的去抖动；切到后台或 `pagehide` 时立即保存（`saveBeforeLeaving`）。
- Studio 显示「保存中 / 已保存 / 失败」：只有媒体存在、`store.stored()` 也返回 true 之后才显示「已保存」（`app.js:430-445`）；写入失败时，`onPersistError` 会提示并把状态改成失败。【代码】
- 需要真机验证的场景：
  - 输入以后在 450 ms 内被强制结束；
  - 系统强制结束 WebView 进程（`webViewWebContentProcessDidTerminate` 是否会重新加载、是否会提示）；
  - 存储空间不足；
  - 连续快速编辑。
- **外壳没有实现 `webViewWebContentProcessDidTerminate`**（在 `Native/Sources/LittleDaysUI/WebShell/*.swift` 里搜索不到）【代码】。WebContent 进程崩溃后，界面可能停在白屏。建议实现这个回调：自动重新加载，并显示「刚才编辑器意外关闭了，内容已经恢复到最后一次保存」。（P1）

### C3. 数据迁移和版本兼容

- `schemaVersion: 1`。`normalizeState` 和 `normalizeMoment` 给新字段补默认值（`model.mjs:178` 起）。新字段一律是可选的，Swift 模型同步更新（近期加的 `skin`、`peaks`、`photoOrder`、`pageOrder` 都是这样做的）【代码】。
- 没有多版本的迁移框架。未知字段是否会在规范化或校验时被保留，**需要补一个单元测试来确认**。
- **最小迁移框架**（等真正需要时再启用）：`migrations = [{from: 1, to: 2, up(state)}]`。
  - 迁移前把 state 写进 `little-days.v1.pre-migrate-<版本>`；
  - 迁移后执行 `validateStateSnapshot`；
  - 失败时保留原数据，进入只读的救援提示。
  - 准备一组旧版本的合成样例（`tests/fixtures/state-v*.json`），每个版本都跑「旧数据能打开」的测试。

## D. P1 删除、撤销和回收站

| 删除操作 | 是否确认 | 能否撤销 | 结论 |
|---|---|---|---|
| 阅读器 / 页面菜单中删除一页 | 有 | **不能**（文案却说可以） | B5 |
| 一天的最后一页或封面（清空这一天） | 有 | 6 秒内可以在提示里撤销，日历里也能恢复；**只有一个槽位**，下一次清空会覆盖它 | 可以接受，但多天删除时只能恢复最后一天 |
| 页面管理批量删除 | 有 | **不能**；删空的几天里只能恢复最后一天 | B5 |
| Studio 里删除页面 / 批量删除 / 删除图层 | 有内容时确认 | Studio 的撤销历史（最多 30 步，离开 Studio 就清空） | 可以接受 |
| 删除书 | 有，「不能恢复」 | 不能，但**只有空书才能删除**（`app.js:7472-7485`） | 安全 |
| 删除习惯 | 有 | 不能，打卡记录和成长卡片一起删除 | Labs 功能 |
| 删除计划 | **没有确认** | 不能 | 低影响，可以加上撤销提示 |
| 媒体文件 | — | 永远不会删除 | 安全，但只增不减 |

**回收站设计（P1，以后再实现）**
- 删除的页面放进 `state.trash = [{kind:"page", page, date, bookId, deletedAt}]`，保留 30 天。
- 设置 →「最近删除」可以恢复。超过 30 天以后才真正移除（只移除页面记录，**媒体不删**）。
- 这些 tombstone 同时为将来的同步删除记录做准备（`STORAGE_ARCHITECTURE.md` 4.10）。
- 「永久删除」需要确认两次。

## F. P1 首次创作体验（UX）

**实际步数**（不包括系统照片选择器里的操作）
- 新用户，选 1 张照片：
  1. 「我自己探索」
  2. 「选今天的照片」
  3. 系统选择器 → 选中 → 添加
  4. 预览 → 保存
  5. 首篇完成卡片
  - 合计约 5 步 App 内点击。
- 选 3 张照片：再多一步分组确认「生成 N 页」，合计 6–7 步。
- 不需要事先创建书本（会自动放进「我的手帐」），第一次启动不会请求任何权限。【代码】
- 如果使用引导里的「开始我的第一篇」，它打开的是「今天怎么记」面板，还要再点一次「照片」，比直接点「选今天的照片」多一步。

**简化建议**（都不新增功能）
1. 引导第 4 步的「开始我的第一篇」**直接打开照片选择器**（等于点「选今天的照片」），省一步。
2. 选的照片都属于同一组时（比如同一个时段），分组预览直接用「一页」，不再停下来问；只有建议分成两组以上时才显示分组步骤，省一步。
3. 首篇完成卡片的「看看我的手帐」去打开刚保存的那一页所在的书，而不是书架。
4. 编辑工具保持渐进式展开：自定义模式默认收起，现在已经是这样。
5. 以「60 秒内完成第一篇」作为测试目标，通过用户测试来验证（见 G），不写成既成事实。

**保存状态**：Studio 里已经有「保存中 / 已保存 / 失败」。「今天的故事」的保存按钮在保存过程中应该显示忙碌状态，并且禁止重复点击（需要检查）。

## I. iPhone Duo 折叠屏适配审查

### I1. 证据

- Mac 上的 Xcode 27.2 有 **iPhone Duo** 模拟器（`iPhone19,4`，运行时 iOS 27.1 起），配置文件里：
  - `supportedProductFamilyIDs = [1]`：属于 iPhone 家族。所以我们这个**只支持 iPhone**的 App（`TARGETED_DEVICE_FAMILY = 1`）会原生运行，不会进入 iPad 兼容模式。
  - 两块竖屏：
    - **外屏**：1398 × 2034 px，3 倍，也就是 **466 × 678 pt**；
    - **内屏**：2007 × 2853 px，3 倍，也就是 **669 × 951 pt**。
  - 支持 `com.apple.CoreSimulator.display.resizableScene`（窗口尺寸可以变化）。
  - 生物识别是 **Touch ID**，不是 Face ID（外壳已经根据 `biometryType` 区分，见 `LittleDaysWebShellView.swift:95-101`）。【实测】
- 用 Xcode 为 iPhone Duo 模拟器做了 Debug 构建：**BUILD SUCCEEDED**。安装后启动，截了外屏：
  - 首页和新手引导正常显示，宽度利用合理；
  - **右上角的状态栏和传感器区域盖住了首页的设置齿轮**（截图保存在 Mac 的 `/tmp/capiday-duo/outer.png`）。
  - 内屏在折叠状态下是关闭的，截图全黑；命令行（`simctl io`）没有找到切换折叠状态的方法，**内屏需要在 Simulator 的菜单里手动展开后再看**，或者用真机。【实测】
- 当前设置：
  - `IPHONEOS_DEPLOYMENT_TARGET = 17.0`；
  - 只支持竖屏；
  - 只有一个场景；
  - WebView 用 `.ignoresSafeArea()` 铺满全屏，安全区交给 CSS 处理；
  - **Swift 不响应尺寸变化**（`updateUIView` 是空的）。【代码】`project.pbxproj:161-229`；`LittleDaysWebShellView.swift:17-18, 175-187`

### I2. 兼容性评估

| 区域 | 外屏（466 pt） | 内屏（669 pt） | 折叠和展开的切换 |
|---|---|---|---|
| 安全区 | **P0**：只用了 `safe-area-inset-top` 和 `-bottom`，**完全没有 `-left` 和 `-right`**；右上角的控件被遮住【实测】 | 需要验证 | — |
| 首页、日历、书架、设置 | 正常 | **P1**：没有最大宽度的内容列（`.home-mag { max-width: 100% }`，`styles.css:8340`），整页铺满；日历每格约 100 × 135 px，6 行将近 800 px；文字行太长 | 内容会重新排版（大多是 CSS），但 JS 里按宽度算出来的值不会更新（例如照片墙的列数 `innerWidth >= 700 ? 3 : 2`，`app.js:1103`，只在渲染时读取） |
| Journal Studio | 纸张大小由高度决定，正常 | 纸张用 `--studio-h` 计算，宽屏上居中，两边留白很大（可以接受）；工具栏和面板占满整个宽度 | **P0**：`--studio-h` 只在 `render()` 时设置（`app.js:6681`），`--strip-h` 也一样（4756）；尺寸变化以后纸张会停在旧的大小，直到下一次渲染。图层的选择框、正在进行的拖动、灯箱的平移（`zoomView`，3031）都是按像素记录的，会错位 |
| 键盘 | 正常 | 正常 | **P1**：尺寸变化时 `innerHeight - vv.height` 可能短暂超过 80，被误判为键盘弹起，或者退出输入状态（`app.js:13290-13295`） |
| 裁剪编辑器 | — | — | P2：每次打开都会添加一个 `resize` 监听，从不移除，会越积越多（`js/crop-editor.mjs:241`） |
| 弹窗和面板 | 正常 | 宽度上限 365–430 px 居中，可以接受（P2：在宽屏上可以改成居中的卡片） | — |
| 手帐内容和导出比例 | 不受影响：百分比坐标、固定 4:5、`cqw` 文字、绘图板固定 1080 × 1350（`draw.mjs:7-8`） | 同左 | 同左；草稿状态和尺寸无关，**不会因为尺寸变化重复保存或丢失草稿**（自动保存只由内容改动触发）【代码】 |

### I3. 适配方案（响应式，不复制页面代码）

1. **安全区（P0）**：在 `.phone`、`.home-top`、`.bottom-nav` 和弹窗上加入 `env(safe-area-inset-left / right)`；页面顶部的操作按钮避开传感器区域。
2. **尺寸变化（P0）**：
   - 加一个统一的 `onViewportChange`（`ResizeObserver(#app-scroll)`，加上 `visualViewport` 的 resize，去抖 100 ms），重新计算 `--studio-h` 和 `--strip-h`；
   - 关闭进行中的拖动和捏合；
   - 重新定位选择框、引导和工具条；
   - 判断「是否需要重新渲染」：照片墙的列数变化时才重新渲染。
   - 尺寸正在变化时暂时停止键盘判断（250 ms）。
3. **宽屏布局（P1）**：在 `min-width: 600px` 时，主内容放进 `max-width: 640px` 的居中列（首页、日历、书架、设置）；日历格子限制最大高度；Studio 的纸张用 `min(宽, (高 − 工具区) × 0.8)`；工具栏居中，最大宽度 560 px。
4. **小屏（P1）**：320–375 pt 时检查 Studio 面板打开后纸张不小于 160 px（现在有一条注释写的是 375 × 667 的假设，`styles.css:15637`）。
5. **Swift**：不需要专门为 Duo 写代码。WKWebView 会自动跟随窗口尺寸；可以选做：在 `viewWillTransition` 或场景尺寸变化时，向页面发一个 `capiday:resize` 事件作为兜底。

### I4. 需要修改的文件（实施时）

`Public/styles.css`（安全区、宽屏的最大宽度、小屏）、`Public/app.js`（`onViewportChange`、`--studio-h` 的重新计算、拖动的取消、键盘判断的保护、照片墙列数）、`Public/js/crop-editor.mjs`（移除监听）、`LittleDaysWebShellView.swift`（可选的尺寸事件），以及新的测试。

### I5. 测试方案

- **自动化**（Chromium）：在 375、466、669、851 宽下各截一次首页、日历、Studio、阅读器、设置；在 Studio 打开时把视口从 466 × 678 改成 669 × 951 再改回来，断言纸张大小更新、图层坐标不变、草稿的 JSON 没有变化、没有退出输入状态。
- **模拟器**：在 iPhone Duo 模拟器上手动折叠和展开（Simulator 菜单），依次走查首页、日历、Studio（正在编辑文字时折叠或展开）、阅读器、设置、照片选择器、分享面板；同时用 iPhone SE、17、18 Pro Max 回归。
- **真机**：拿到 Duo 后重复上面的走查，另外检查 Touch ID 解锁 App 锁和键盘。

### I6. 复杂度

安全区：低。尺寸变化处理：中（集中在 Studio）。宽屏的最大宽度：中（CSS 为主）。总共约 3–4 天，加上走查。
