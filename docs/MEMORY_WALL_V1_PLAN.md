# Memory Wall 照片墙 v1.0 · 产品需求与开发计划

> **状态：Planned — Post-Alpha Stability**（已规划，等 Alpha 稳定性修复完成后再开发）。
> 2026-11-15。本文只做代码检查、需求整理和方案设计：**没有修改照片墙、Journal Studio、数据库或存储结构**，也没有写任何功能代码。
> 任务 ID 和状态以 [DEVELOPMENT_TRACKER.md](DEVELOPMENT_TRACKER.md) 第 6 节为准。
> 代码位置以 commit `a3cea07`（V10.75）为准；行号以后会漂移，以函数名为准。

产品方向（Founder 已确定）：**方案 A · 自动生成 + 自由管理（Auto + Curate）**——自动记录，自己决定如何展示。照片墙是用户手帐作品的展示空间，不是另一个日历，也不是独立的照片上传工具。

## 1. 当前实现（代码核对）

| 项目 | 现状 | 位置 |
|---|---|---|
| 入口 | 日历页的分段按钮「照片墙」（`calendarMode = "wall"`，不保存，重开 App 回到「生活记忆」） | `app.js` `calendarHTML`、`calendar-mode` |
| 收集逻辑 | 纯函数 `wallPhotos(state)`：只读 `state.entries`（**不读草稿、不读示例日**）；收集一天的 `entry.photo`、每页的照片图层（不含手绘）和照片背景；只收 `media:` / `data:` 引用 | `Public/js/photo-wall.mjs` |
| 不收集 | 内置图库照片（`photo:`）、视频、音频；手机相册里没有加进手帐的照片（App 从不读取相册） | 同上 |
| 去重 | 按引用字符串（`media:<uuid>`）全局去重：同一个文件放在两本手帐里只出现一次（显示第一次出现的位置）。**重新导入的同一张照片**是新的 uuid，会出现两次 | 同上 |
| 排序 / 分组 | 按 `entry.date` 从新到旧，同一天内页面倒序；`wallMonths` 按月份分组；没有使用拍摄时间 `capturedAt` | 同上 |
| 布局 | JS 瀑布流：手机 2 列、宽度 ≥ 700 px 时 3 列（`wallColumns`）；**没有虚拟列表** | `photo-wall.mjs`、`app.js` `photoWallHTML` |
| 加载 | `watchPhotoWall`：IntersectionObserver 懒加载，最多同时 3 张；缩略图 ≤ 480 px 的 blob URL | `app.js` |
| 点击 | `openWallViewer` 大图；「打开这一页」→ `openWallPage` → `openReader(date|momentId)`，保留和原始手帐的关联 | `app.js` |
| 按手帐筛选 | 顶部手帐 chips（`calendarBookChips`） | `app.js` |
| 卡片数据 | `{id, ref, date, bookId, momentId, layerId}` | `photo-wall.mjs` |
| 管理 / 隐藏 / 排序 / 整页卡片 | **都没有** | — |
| 测试 | `tests/v152-browser.cjs`（浏览器）；`photo-wall.mjs` 没有单元测试 | — |

和 v1.0 相关的现有系统：

- **页面渲染**：`canvasHTML` / `sharedCanvasHTML(page, ctx, {readOnly})` 自己按容器缩放（`aspect-ratio: 4/5`、`container-type`、`cqw` 单位）。阅读器缩略图 `.reader-thumb`、书本页的 `.day-page-thumb` 已经用它画小尺寸的整页，**整页卡片可以直接复用**，不需要另写一套渲染。
- **页面 ID**：页（moment）的 id 是 `crypto.randomUUID()`，全局唯一；图层 id 在重新排版时保持不变，但自动生成的装饰图层（`gen`）会重新生成。代码里**没有修改一天或一页日期的入口**（按拍摄时间选照片时会直接打开那一天，不是移动）。
- **存储**：整份手帐是 IndexedDB `little-days-meta` 里的一个 JSON（`state`）；媒体在 `little-days-media`。
- **备份**：JSON 备份里的 `state` 是整份 `structuredClone(state)`，新加的顶层键会自动包含；但媒体只按固定的 `visitMediaReferences` 列表收集和改写（`media.mjs`），所以**照片墙配置里不要存 `media:` 引用**（见 3.2）。
- **原生层**：照片墙完全在 `Public/`，外壳只加载页面；v1.0 不需要原生代码。

## 2. 计划新增（v1.0）

| ID | 功能 | 级别 | 要点 |
|---|---|---|---|
| MW-01 | 自动生成照片墙 | P0 | 保留现有全部行为；不重复生成同来源卡片；不读手机相册；不破坏现有功能 |

## 3. 技术方案

### 3.1 原则

- 照片墙仍由 `wallPhotos(state)` **每次从手帐计算**；新增的只是一份很小的「展示配置」，叠加在计算结果上（隐藏、整页、顺序）。配置坏了或没有，照片墙就退回现在的样子。
- 配置里只存**来源 ID**，不存图片、不存页面副本、不存 `media:` 引用。
- 不改现有的 entries / moments / layers 结构；新增一个可选的顶层键（加字段属于「新增可选字段」，旧数据没有它时等于默认值）。这一步在 Stage 1 经 Founder 确认后才做。

### 3.2 建议的数据模型（Stage 1 确认后才实施）

```js
state.wall = {            // 可选；没有 = 现在的照片墙
  version: 1,
  order: "time",          // "time" | "custom"
  hidden: {               // 被隐藏的卡片：key → 隐藏时间
    "photo:<momentId>:<layerId>": "2026-12-01T10:00:00Z",
    "photo:day:<date>": "…",            // 一天的 entry.photo（没有页 id）
  },
  pages: [                // 贴到照片墙的整页
    { key: "page:<momentId>", addedAt: "…" },
    { key: "page:day:<date>", addedAt: "…" },   // 一天的封面页
  ],
  custom: ["page:<id>", "photo:<id>:<layer>", …],   // 自定义顺序（只列出排过的卡片）
  updatedAt: "…",
};
```

- **来源 key**：照片 = `photo:<momentId>:<layerId>`（背景用 `photo:<momentId>:backdrop`），整页 = `page:<momentId>`。momentId 是全局 UUID，**不包含日期**，所以和日期无关；也**不包含 media id**，所以恢复备份时媒体被重新编号也不受影响。
- 同步更新 Swift `Packages/LittleDaysCore` 的 `Models.swift`（可选字段）和 Core 测试（AGENTS.md 要求）。
- 校验：`validateStateSnapshot` 和恢复检查对 `wall` 只做宽松检查（是对象、各字段类型对），不合格时**忽略配置**而不是拒绝整份手帐。
- 读取时清理：key 找不到来源的条目不显示（不删除，留着等内容回来，例如撤销删除；可以在保存配置时顺手去掉超过一定数量的失效项）。

### 3.3 关键文件

| 文件 | 改动（Stage 2） |
|---|---|
| `Public/js/photo-wall.mjs` | `wallPhotos` 给每张卡片加 `key`；新增纯函数 `applyWall(cards, wall, state)`：去掉隐藏的、加入整页卡片、按模式排序；单元测试 |
| `Public/app.js` | 管理模式 UI（选择、隐藏、已隐藏列表、恢复、拖动排序）；阅读器 / 页面菜单「贴到照片墙」「从照片墙移除」；整页卡片用 `sharedCanvasHTML(readOnly)` 渲染 |
| `Public/styles.css` | 管理模式、整页卡片的边框 / 纸张感、拖动状态 |
| `Public/js/model.mjs` | `normalizeState` 保留 `wall`；宽松校验 |
| `Public/js/restore-safety.mjs` | 恢复预览里显示「照片墙设置」；旧备份没有它也能恢复 |
| `Models.swift` + Core 测试 | 可选字段 `wall` |
| `i18n.json` | 中英文文案 |

不改：Journal Studio、页面数据结构、媒体库、备份格式版本。

### 3.4 整页卡片的渲染

- 复用 `sharedCanvasHTML(page, ctx, { readOnly: true })`，和阅读器缩略图同一套代码，所以**显示一定和原页面一致**；页面改了，下次渲染就是新的样子（不存截图）。
- 性能：整页卡片比照片贵（多个图层、字体）。只在卡片进入视口时渲染（沿用 `watchPhotoWall` 的 IntersectionObserver），离开很远时换成占位；整页卡片数量建议设上限（例如 50，**需要确认**）。
- 视觉区分：整页卡片用 4:5 的纸张比例、细边和小角标「整页」；照片卡片保持现在的样子。

## 4. 13 个边界情况

| # | 场景 | 预期行为 | 技术风险 | 推荐方案 | 需要 Founder 确认 |
|---|---|---|---|---|---|
| 1 | 同一张照片出现在不同手帐中 | 照片墙只出现一次 | 现在按 `media:` 引用去重；重新导入的同一张照片是不同的 id，会出现两次 | 保持按引用去重；隐藏时按「这张照片」隐藏（同一引用的所有位置一起隐藏）。重复导入的照片按内容去重需要 SHA（`little-days.media-sha` 已有索引），放到 v1.1 | **是**：隐藏一张时，同一照片在别处的位置是否一起隐藏（推荐一起） |
| 2 | 隐藏照片后又修改原始手帐 | 修改文字、排版、加别的照片：这张照片仍隐藏；新加的照片照常出现 | 图层 id 稳定，key 不变；自动排版重新生成的装饰图层（`gen`）不是照片，不影响 | key 用 `momentId:layerId` | 否 |
| 3 | 删除原始手帐页面 | 照片 / 整页卡片从墙上消失，不出现坏卡片；撤销删除后回来 | 配置里的 key 失效 | 读取时找不到来源就不显示，配置条目保留一段时间（撤销 / 恢复时能回来） | 否 |
| 4 | 替换原始照片 | 推荐：同一位置换了照片，**新照片照常显示**（隐藏的是「那一张」） | 替换时图层 id 不变而 `mediaRef` 变了；只按位置 key 会把新照片也隐藏 | 隐藏记录同时存当时的「照片指纹」（引用的 SHA 前 16 位，不是 media id）；不一致就视为新照片 | **是**：替换后的新照片是否继续隐藏 |
| 5 | 整页卡片添加后原始页面变化 | 卡片显示最新的页面 | 无（实时渲染） | 不存截图，直接渲染 | 否 |
| 6 | 自定义排序期间出现新照片 | 见第 6 节 MW-04 问题 1 | 新卡片不在 `custom` 列表里 | 不在列表里的卡片按时间插到一个固定位置（候选方案见第 6 节） | **是** |
| 7 | 修改手帐日期 | 照片墙按新日期排在新的位置；隐藏 / 整页设置不丢 | 现在**没有改日期的入口**；以后加了也没关系，因为 key 不含日期 | key 只用 momentId / layerId | 否（以后加改日期功能时复查） |
| 8 | 备份恢复到另一台设备 | 照片墙设置跟着恢复 | 恢复时媒体可能重新编号 | `state.wall` 在 `state` 里，已在 JSON 备份中；key 不含 media id，不需要改写 | 否 |
| 9 | 老版本备份没有照片墙配置 | 恢复后照片墙 = 自动生成（全部显示、时间排序） | 恢复是「替换」，会把当前的照片墙设置换成「没有」 | 恢复预览里写明「这个备份没有照片墙设置」 | **是**：恢复旧备份时是否保留本机现有的照片墙设置（推荐：不保留，和其他数据一样整体替换，但在预览里说明） |
| 10 | 单页手帐包含大量照片 | 每张照片一张卡片；整页卡片仍是一张 | 一页 20+ 照片让墙被一页占满；整页卡片渲染很重 | 照片卡片沿用懒加载；整页卡片里的照片用照片墙已有的 ≤480 px 缩略图（`sharedCanvasHTML` 现在是否走缩略图要在 Stage 1 核对） | 可选：一页最多上墙几张照片 |
| 11 | 很长的中文或英文文字 | 整页卡片和原页面一样（文字按页面比例缩小） | 小卡片里文字很小，看不清 | 照原样缩小（「作品」展示）；点开看完整页面 | 否 |
| 12 | 特殊字体或中英文混排 | 和原页面一样 | 字体没加载完时短暂用备用字体 | 复用阅读器的字体加载；卡片在字体就绪后显示 | 否 |
| 13 | 数百到数千张照片 | 滚动流畅，打开不卡 | 现在**没有虚拟列表**：所有卡片 DOM 一次画出；数千张时首屏和内存都有压力；`wallPhotos` 每次全量计算 | Stage 2 先测 500 / 2000 / 5000 张合成数据；超过阈值时按月份分段渲染（只渲染视口附近的月份）；`wallPhotos` 结果按 state 版本缓存 | 否（性能目标见第 7 节） |

## 5. 风险

| 类别 | 风险 | 对策 |
|---|---|---|
| 数据安全 | 照片墙操作误改原始数据 | 照片墙代码**只写 `state.wall`**；测试断言每次操作后 entries / books / drafts 完全不变 |
| 数据安全 | 配置引用 media id，恢复后失效；或被 `visitMediaReferences` 漏掉 | key 只用 momentId / layerId，不存 `media:` |
| 数据安全 | 坏的配置导致手帐打不开 | 宽松校验，坏配置只被忽略 |
| 性能 | 数千张照片无虚拟列表；整页卡片渲染重 | 分月渲染、懒渲染、整页卡片上限；性能测试 |
| 渲染 | 整页卡片和原页面不一致 | 只用 `sharedCanvasHTML`，不写第二套 |
| 手势 | 长按拖动和页面滚动、iOS 长按菜单冲突 | 只有管理模式里才能拖；拖动手柄 / 长按 350 ms；`touch-action` 和 `-webkit-touch-callout: none`；真机验证 |
| 兼容 | 旧版本 App 打开新数据 | 新键是可选的，旧版本会忽略（需在 Stage 1 确认旧版本的 `normalizeState` 不会因为未知键报错——当前代码保留未知键） |

## 6. 待 Founder 确认

**MW-04 排序（按要求只分析，不自行决定）**：

1. **自定义排序时新增照片放在哪里？**
   - A. 放在最前面（像相册「最新」）：新内容最容易看到；推荐。
   - B. 放在最后。
   - C. 按时间插入到时间顺序上对应的位置（自定义顺序中间可能出现不在预期的位置）。
2. **自定义排序是否保留月份分组？**
   - A. 不保留：自定义就是一面整体的墙，没有月份标题；推荐（月份标题和自由顺序互相矛盾）。
   - B. 保留：只能在同一个月内拖动。
3. **重新编辑旧手帐后是否改变排序？**
   - 推荐：不改变。编辑不改日期、不改 key，时间排序和自定义排序都不动。
   - 例外需要决定：编辑时**新加**的照片算「新增照片」（按问题 1 的答案放）。
4. **恢复时间排序后能否再次使用之前的自定义顺序？**
   - A. 可以：切回「自定义排序」时恢复上次的顺序（`custom` 列表保留）；推荐。
   - B. 不可以：恢复时间排序 = 清掉自定义顺序（需要二次确认）。

**其他**：

5. 隐藏一张照片时，同一照片在别的手帐里的位置是否一起隐藏（边界 1，推荐一起）。
6. 替换原始照片后，新照片是否继续隐藏（边界 4，推荐不隐藏）。
7. 恢复旧备份时照片墙设置是否整体替换（边界 9，推荐整体替换 + 预览说明）。
8. 「贴到照片墙」入口放在哪里：阅读器「···」菜单（推荐）/ 页面菜单 / Studio 预览（Studio 本次不改）。
9. 整页卡片数量上限（建议 50）和一页最多上墙几张照片（建议不限）。
10. 照片墙模式是否在重开 App 后记住（现在每次回到「生活记忆」）。

## 7. 开发顺序（Alpha 完成之后）

- **Stage 0（现在）**：Alpha 稳定性修复，**不开发照片墙**。
- **Stage 1 · 架构与交互设计**：Founder 回答第 6 节；确认数据模型（3.2）；画管理模式和整页卡片的设计板；写回归测试方案；500 / 2000 / 5000 张的性能基线（只测量，不改代码）。提交方案等 Founder 确认。
- **Stage 2 · 分批开发**（每一步先验证再进入下一步）：
  1. MW-02a 照片隐藏与恢复（`state.wall.hidden` + `applyWall` + 单元测试）
  2. MW-02b 管理模式 UI
  3. MW-03 整页卡片（贴到照片墙 / 移除 / 点开 / 回到原记录）
  4. MW-04 自定义排序（按 Founder 的答案）
  5. MW-05 备份与恢复支持（恢复预览说明、旧备份、Swift 模型）
- **Stage 3 · 回归测试**：
  - 单元：`applyWall`（隐藏、整页、排序、失效 key、坏配置）、`wallPhotos` key 稳定性；
  - 浏览器：自动收集正常、不重复、隐藏 / 恢复、整页一致（与阅读器缩略图逐像素比较）、原始手帐不变、排序保存、重开 App、备份恢复（含旧备份、媒体重新编号）、Calendar / Studio / My Books 回归；
  - 性能：5000 张合成照片首屏 < 1 s、滚动无长任务（> 50 ms）；
  - 真机：触摸、长按拖动、滚动、键盘无关、最大字号。
